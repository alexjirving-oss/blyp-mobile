# Live Repair Report

## Root cause(s)
- Viewer rendering reused the host render surface (`IVSBroadcastModule.setRenderSurface`), so viewer surfaces overwritten host preview and never bound a dedicated surface for remote tracks; the Real-Time view also ignored its props, leaving the viewer path effectively sharing host plumbing ([android/app/src/main/java/com/blyp/mobile/ivs/IVSRealTimeView.kt#L22-L33](android/app/src/main/java/com/blyp/mobile/ivs/IVSRealTimeView.kt#L22-L33), [android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastViewManager.kt#L30-L51](android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastViewManager.kt#L30-L51), [android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L852-L884](android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L852-L884)).
- Viewer pipeline lacked first-frame / surface-attachment observability and reconnection guardrails, making it hard to confirm rendering or recover from drops ([android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L561-L585](android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L561-L585), [android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L794-L797](android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L794-L797), [src/live/ivs/hooks/useIVSViewerSession.ts#L282-L303](src/live/ivs/hooks/useIVSViewerSession.ts#L282-L303)).

- Viewer (IVS Real-Time): LiveStreamScreen viewer route renders `LiveStreamViewer` → `useIVSViewerSession` grabs viewer token via `joinLiveRealtime` and joins the stage through `IVSNativeClient.joinAsViewer` → `IVSBroadcastModule.joinAsViewerReadOnly` → `startViewerSession`; the dedicated Real-Time view now binds the viewer surface for stage rendering ([src/components/LiveStreamViewer.js#L171-L234](src/components/LiveStreamViewer.js#L171-L234), [src/live/ivs/hooks/useIVSViewerSession.ts#L58-L168](src/live/ivs/hooks/useIVSViewerSession.ts#L58-L168), [src/streaming/IVSNativeClient.ts#L463-L510](src/streaming/IVSNativeClient.ts#L463-L510), [android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L356-L394](android/app/src/main/java/com/blyp/mobile/ivs/IVSBroadcastModule.kt#L356-L394), [android/app/src/main/java/com/blyp/mobile/ivs/IVSRealTimeView.kt#L17-L33](android/app/src/main/java/com/blyp/mobile/ivs/IVSRealTimeView.kt#L17-L33)).
- HLS paths still reachable: `LiveStreamViewer` falls back to the IVS Player view or the legacy HLS/TikTok-style viewer when Real-Time is unavailable, and `IVSNativeClient.joinAsViewerPlayback` remains exposed for playback URLs ([src/components/LiveStreamViewer.js#L186-L247](src/components/LiveStreamViewer.js#L186-L247), [src/components/LiveStreamViewer.js#L252-L470](src/components/LiveStreamViewer.js#L252-L470), [src/streaming/IVSNativeClient.ts#L501-L541](src/streaming/IVSNativeClient.ts#L501-L541)).

## How to test on two devices
1) Host device (Android dev client with IVS): open the live screen as host, start stream, confirm host preview renders; watch logs for `[IVS_HOST]` and `[IVS_SURFACE_READY]` and ensure no errors. 
2) Viewer device (Android dev client with IVS): open the same stream via viewer route; expect `[IVS_VIEWER][STAGE_JOIN_SUCCESS]`, `[IVS_VIEWER][REMOTE_TRACK_ADDED]`, and `[IVS_VIEWER][FIRST_FRAME_SIGNAL]` logs, with video rendering inside the Real-Time viewer view. 
- Network drop check: briefly toggle airplane mode on the viewer; ensure the viewer auto-reconnect attempts appear (capped at 3) and video resumes when connectivity returns.
- Regression guard: verify HLS fallback still plays when IVS Real-Time is unavailable by forcing `streamingConfig.backend` off IVS.
